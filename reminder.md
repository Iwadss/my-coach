## 14. 2026-09-06 — Cancelling a booking didn't actually free the slot

Reported bug: book a slot, cancel it from My Sessions, then try to book that exact same slot again — "Time slot already booked." Not a frontend state bug — `handleCancel` in `ClientSessions.tsx` was already doing the right thing (`UPDATE bookings SET status = 'cancelled'`, gated by the `bookings_client_cancel` RLS policy, which only permits that exact transition). The bug was the DB constraint: `bookings_coach_id_date_time_slot_id_key` was a **plain** unique constraint on `(coach_id, date, time_slot_id)` with no awareness of `status`, so a cancelled row permanently occupied its slot forever — a fresh insert hit the same 23505 unique violation as a genuine double-booking would.

**Fix** — migration `20260906000000_free_slot_on_cancel.sql`: dropped that constraint and replaced it with a partial unique index, `... WHERE status <> 'cancelled'`. ## 30. 2026-09-03 — Token-based booking: 1 token = 1 hour, enforced at the database, not just the UI

The biggest change of this whole session so far — a real payment-gate primitive across the client booking flow, the coach's client roster, and the earnings page. Payment collection itself stays external/manual exactly as asked; what's new is a real, enforced *balance* that gates booking.

**Design call, made deliberately rather than the obvious first instinct:** the natural-sounding implementation is "insert the booking, then separately update the token count" from `ClientBook.tsx`'s own code. Didn't do that — two sequential client-side writes for something money-adjacent is exactly the kind of gap this project has hit before (see §14's free-slot-on-cancel bug, born from a similar "should be fine" assumption). Went with database triggers instead, migration `20260909000000_token_based_booking.sql`:

- **`clients.token_balance`** (`int, default 0, check >= 0`) — the spendable balance.
- **`clients.tokens_issued_total`** (`int, default 0, check >= 0`) — a running total that only ever goes up, incremented solely by manual coach adds. This is what makes "Tokens Issued" on the Earnings page a real historical figure instead of just re-deriving it from the current (net) balance, which would be wrong the moment any tokens had been used.
- **`bookings_deduct_token_trigger`** (`before insert on bookings`) — locks the client's row (`select ... for update`), checks the balance, decrements it, or raises `'Not enough tokens to book this session'` and aborts the insert entirely if it's already 0. The row lock means two tabs racing to spend a client's last token can't both succeed — the second transaction blocks, re-reads the now-zero balance, and correctly fails.
- **`bookings_refund_token_trigger`** (`after update of status on bookings`, `when (new.status = 'cancelled' and old.status is distinct from 'cancelled')`) — refunds 1 token on the one real transition into cancelled. The `WHEN` clause means it's structurally impossible to double-refund by cancelling an already-cancelled row twice.
- **`coach_adjust_client_tokens(p_client_id, p_delta)`** — the only door in for a coach's manual Add/Deduct. Checks the caller is that client's approved coach (or admin) before touching anything.

The upshot: **neither a client nor a coach has any direct write grant on `token_balance` at all** — no column-level grant exists for it on either side. Every legitimate change goes through a trigger (which runs with the elevated privilege of a `security definer` function, same pattern this schema already uses for `admin_set_coach_status` etc.) or through the one RPC, which enforces its own authorization. This isn't just enforced by a disabled button — confirmed by logging in as a real client over the raw REST API and attempting to insert a booking directly with 0 tokens: rejected with the same message, no UI involved.

**`coaches.hourly_rate`** (`numeric, nullable`) was also added — needed to turn "tokens used" into a dollar figure on Earnings, and there was nowhere in the schema to put a coach's rate before this. Nullable and coach-settable directly (not RPC-gated — unlike token balances, a coach misdeclaring their own rate isn't a security concern, just a display of their own number), with the Earnings page honestly saying "set your rate" rather than assuming $0 when it's unset — same "don't fabricate, don't silently assume" instinct this project has kept throughout.

**Client Management (`client-management.tsx`).** Each roster card now shows a token-count pill (green if >0, red if 0 — a coach scanning the list can immediately see who's blocked from booking) alongside the existing session count. The detail dialog gained a "Token balance" row and an "Adjust tokens" button, which opens a small nested modal (amount input + separate "− Deduct" / "+ Add" buttons, exactly the two distinct actions asked for) that calls `coach_adjust_client_tokens` and updates both the roster list and the open detail dialog immediately on success — no refetch needed.

**Coach Earnings (`CoachEarnings.tsx`) — full rebuild,** not an edit. The old version's empty "Client payments" table (with an honest comment explaining there was no real payment data to show yet) is now genuinely populated: a per-client table of Issued / Used / Balance, two summary cards ("Tokens issued" and "Tokens used / completed" — the latter is literally each client's `completed_slots` from `client_booking_totals`, summed, since 1 token = 1 hour = 1 completed session), and an "Estimated earnings" card computing `tokens used × hourly rate` with an inline rate input/save control. The subscription "Your plan" card from the old version stayed untouched below it — unrelated, still real.

**Client booking flow (`ClientBook.tsx`).** A token banner sits above Step 1, always showing the current balance, and switching to the exact requested red warning — "You have 0 tokens. Please contact your coach to purchase more sessions." — when it's zero. The "Tokens left" count also appears in the persistent "Your booking" summary card regardless of which step the client is on. The Confirm button is genuinely `disabled` (not just styled) whenever `tokenBalance === 0`, on top of the existing time/workout-type requirements, and its label changes to "No tokens left" to explain why. `handleConfirm` also catches the trigger's own rejection message as a backstop — for the case where the balance goes stale (spent in another tab since the page loaded) — and shows the same warning rather than a generic error.
